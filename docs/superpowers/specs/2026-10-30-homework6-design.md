## Дані, суми й реальний API

- Додаємо моделі та чистий `consolidatePreOrder()` з архіву, зберігаючи оригінальні навчальні тести.
- Картки показують свої subtotal. Grand Total і список ресторану рахуються з підтверджених внесків, не з `sessions.total`: у контрольному прикладі $540, а не $760.
- Важлива сумісність: наш backend додає особистий Order власника до консолідації незалежно від `isSubmitted` Owner-сесії. На межі API нормалізуємо особистий внесок Owner для відображення й консолідації; чернетки Guest залишаються виключеними. Додаємо регресійну перевірку цього випадку.
- Сервіс надає точні методи офіційних тестів: `getGroupInvite$`, `getSessions$`, `getOwnerSessionId$`, `getStatus$`, `submit$`, `removeSession$`. Якщо старі виклики ще потрібні, тонкі сумісні методи делегують тим самим HTTP-операціям.
- Звичайні запити використовують чинний tokenInterceptor для помилок. Тихі sessions/status передають `HttpContext` із `SKIP_ERROR_TOAST=true`; гостьова гілка interceptor також мусить поважати цей контекст.
- Не створюємо Order приховано під час Submit: помилка реального API про відсутній Order показується користувачу. Наявна явна підготовка legacy-групи залишається окремою дією.
- Важлива сумісність: публічний invite API нашого backend відхиляє вже submitted/closed або заповнену групу. Звичайний шлях `invite-token → invite` зберігається для моків і офіційних тестів. Для цих обмежень реального API сервіс використовує owner-authorized session metadata та деталі бронювання як fallback, щоб власник міг повторно відкрити надіслане замовлення. Fallback не обходить перевірки власника й не маскує справжній 404.

## Деморежим

- Переносимо `?demo` login, mock interceptor і mock store з архіву та їхні тести.
- Demo initializer і interceptor реєструються лише в development. Production не повинен авторизувати `?demo` або відправляти демотокен до справжнього API.
- Моки обробляють лише демо-ID та необхідні запити демокористувача. Інші ID із реальною авторизацією працюють з AWS.
- `http://localhost:4200/reservations/demo-reservation/group-order?demo` відкривається без backend/account. Мок скидається при перезавантаженні.
- Development API URL налаштовуємо на наш AWS API; production як і раніше бере `BACKEND_URL` під час build.

## Стани й дії

- Початковий loading; помилки 404 «Group reservation not found», інші помилки й «Try again»; порожній список страв — «Participants haven't added any dishes yet».
- Owner-картка — «My Pre-Order» за owner session ID.
- Open → «Collecting pre-orders», Submitted → «Sent to Restaurant»; Closed теж read-only.
- Плашка про кількість непідтверджених кошиків, із правильною одниною/множиною.
- Submit Pre-Order відкриває спільний app-modal з Submit/Cancel. Порожня консолідація й запит у процесі блокують Submit. Подвійний клік не дублює POST.
- Успіх: toast «Pre-order sent to the restaurant», read-only екран. Помилка: зберігаємо дані, дозволяємо повторити, toast від interceptor не дублюємо.
- Remove Guest лише для Guest у Open, aria-label «Remove <name>», app-modal з іменем і попередженням. Після DELETE замінюємо snapshot відповіддю сервера. Після Submit кнопок видалення немає.

## Синхронізація

- Поки Open, раз на 15 секунд оновлюємо sessions і status; кнопка Refresh використовує той самий цикл оновлення.
- Один таймер на екземпляр сторінки. Try again не створює другого. Після Submit/Closed і при destroy таймер зупиняється.
- Запити не перекриваються; manual refresh також не запускає другий запит поверх поточного. Під час submit/delete не застосовуємо застарілі результати фонового refresh.
- Фонове оновлення не прибирає картки й не показує початковий full-page loader.
- Показуємо «Updated at …». При фоновій помилці лишаємо останній успішний snapshot і «Couldn't refresh. Showing data from …», без повторних toast.
- Додаткові перевірки понад готові тести: повільна HTTP-відповідь, повторний Try again, зовнішня зміна статусу, перетин refresh і mutation.
